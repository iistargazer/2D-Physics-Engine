# Benchmarks and measured evidence

Recorded tables below are transcribed from local receipts under `build/`; they were not
remeasured during the documentation pass. Interpretation is distinguished from measurement. Where a measurement shows the engine failing,
the failing row is reproduced rather than deleted.

The regression suite is the other half of the evidence: `build/final_tests.log` records
143 passing checks (that count is the number of `ok:` lines in the log; the suite itself
prints only `ALL TESTS PASSED (0 failed)`, so count the lines in your own run).

## What the recorded measurement revision contains

The continuous-collision impact rule changed (a swept impact is now resolved as a
centre-of-mass impulse instead of an impulse applied at an approximate contact point),
so the five benchmark CSVs were regenerated at that engine revision. Three schema-level changes matter when reading them:

- `build/showcase.csv` now has one row per showcase scene (ten rows) and a wider set of
  columns, including CCD counters and the awake count at the end of the run.
- `build/ccd.csv` now reports `capped_trials = 0` for every row, circles and thin tilted
  polygons alike: no event budget was exhausted. This CSV does not report clamp/push-out
  counters; idle nets in specific wall cases are separate suite assertions. The previous revision of this document recorded `capped_trials = 100`
  on the polygon rows; that behaviour is gone.
- The showcase car scene carries a persistent wheel `driveTorque` now, so the benchmark
  no longer applies an external torque to drive it.

Cross-session timing comparisons are not valid. The same `benchmark_broadphase` dense
10k row recorded 71.757600 ms `tree_step_ms` in the previous revision of this document
and 177.565200 ms in this one, while the sparse 10k row moved the other way
(9.216200 ms then, 2.997600 ms now). The host was shared both times. Only comparisons
inside one CSV still have host noise; do not infer a regression or speedup across sessions
without controlled repeated measurements.

## Machine and build

- Compiler line, printed by `benchmark_broadphase` itself:
  `Compiler: 13.2.0; scalar: double; dt: 1/60; median warm-frame timings`
- Full compiler banner on the measurement host: `g++.exe (Rev3, Built by MSYS2 project) 13.2.0`
- Platform: Windows x86-64, MSYS2 UCRT64 toolchain, no GPU or timing harness involved.
- Scalar type: `double` (`phys::real`).
- Flags: `-std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror`.

Timings are single-threaded wall-clock milliseconds measured on a shared developer
machine. One run of each benchmark is recorded here; see the caveats at the end.

## How to build and run

Direct compiler invocations (no CMake needed, repository root, Bash/Git Bash):

```bash
set -euo pipefail
mkdir -p build
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror -I. benchmark_broadphase.cpp -o build/benchmark_broadphase
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror -I. benchmark_stability.cpp  -o build/benchmark_stability
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror -I. benchmark_joints.cpp     -o build/benchmark_joints
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror -I. benchmark_ccd.cpp        -o build/benchmark_ccd
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror -I. benchmark_showcase.cpp   -o build/benchmark_showcase
```

Capture the CSVs exactly as summarised below, keeping the exit status of each program:

```bash
set -euo pipefail
./build/benchmark_broadphase > build/broadphase_benchmark.csv
./build/benchmark_stability  > build/stability.csv
./build/benchmark_joints     > build/joints.csv
./build/benchmark_ccd        > build/ccd.csv
./build/benchmark_showcase   > build/showcase.csv
```

CMake exposes the same programs as targets named after the files
(`benchmark_broadphase`, `benchmark_stability`, `benchmark_joints`, `benchmark_ccd`,
`benchmark_showcase`), so the equivalence is:

```bash
cmake -S . -B build/cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build/cmake --target benchmark_broadphase benchmark_stability benchmark_joints benchmark_ccd benchmark_showcase
```

Print a compact aligned summary of all CSVs at once:

```bash
python tools/summarize_benchmarks.py
python tools/summarize_benchmarks.py build/broadphase_benchmark.csv build/ccd.csv
```

Two programs are correctness gates as well as timers, and both are checked in their
sources: `benchmark_ccd` returns 1 if any trial lets the projectile end past
`x > 0.1`, and `benchmark_broadphase` returns 1 if the tree and the all-pairs oracle
disagree on the candidate or contact count. A non-zero exit means the run is not valid
evidence, whatever it printed.

## Joint chains

Source: `build/joints.csv`, generated by `benchmark_joints.cpp`. 600 fixed steps at 40
solver iterations; `max_anchor_error` is the worst anchor separation seen in any frame.

| links | iterations | mean_ms | max_anchor_error |
|---:|---:|---:|---:|
| 10 | 40 | 0.009264 | 0.003052 |
| 100 | 40 | 0.158798 | 3.021928 |

The 100-link row is a limitation, not a feature: 3.02 m of anchor error is not an
acceptable rope or bridge. The cause is visible in `Scenes.hpp` — `makeChain` runs the
default solver configuration, which solves the joints as impulses only and leaves
position projection off, so 40 sweeps of a 100-link chain cannot keep up with its own
weight. The suspension bridge scene goes the other way and turns projection on
(`positionIterations = 60`): `build/showcase.csv` reports its worst anchor error as
0.010674 m over 240 frames, and the suite checks the same scene against a 0.02 m bound,
printing "100-plank bridge projection max anchor error=0.010674" in
`build/final_tests.log`.

## Continuous collision, thin-wall trials

Source: `build/ccd.csv`, generated by `benchmark_ccd.cpp`. 100 trials per row against a
0.02 m thick static wall at 200 / 1000 / 10000 m/s; `max_events` is the largest number of
resolved impacts seen in a trial and `capped_trials` counts trials that reported a
non-zero `ccdStats.capped`.

| shape | speed | mean_step_ms | max_events | capped_trials |
|---|---:|---:|---:|---:|
| circle | 200 | 0.019826 | 1 | 0 |
| circle | 1000 | 0.004259 | 1 | 0 |
| circle | 10000 | 0.004834 | 1 | 0 |
| polygon | 200 | 0.008587 | 1 | 0 |
| polygon | 1000 | 0.016565 | 1 | 0 |
| polygon | 10000 | 0.005267 | 1 | 0 |

No trial crossed the wall (the benchmark would have exited 1), every trial resolved its
impact as a single event with zero event caps. That CSV does not establish idle clamps
or push-outs. The suite separately asserts idle nets/rest for circles and nonspinning
tilted polygons at three speeds; its spinning plate stops translation but retains 60 rad/s.
Centre-of-mass impacts avoid fabricated torque while omitting correct off-center torque;
no joint-aware/general frictional-impact acceptance follows from these rows.
The timings in this table are dominated by process noise: a single 1/60 s step of a
two-body world is a few microseconds of work, and the spread between rows runs the wrong
way with speed (0.019826 ms at 200 m/s against 0.004259 ms at 1000 m/s).

Reading the table:

- `mean_ms` is the average over the whole run, so for most scenes it covers the
  transient, not a steady state. Scene 7 is the deliberate exception: over 600 frames it
  settles and then sleeps, ending with `awake_end = 0`, meaning all 5,000 dynamic boxes

  and must not be quoted as a steady-state cost.
- The historical `testStressSleeping` receipt timed 30 early steps (21.5722 ms),
  570 settling steps, then 120 settled steps (15.1470 ms). Its 66.0 reciprocal was
  simulated-step throughput, not rendered FPS; it compared different motion states.
  Current behavioral tests retain sleeping correctness only. The dedicated

- Scenes 0-6, 8 and 9 do not enable sleeping, which is why `awake_end` is close to the

  collapses.
- Ragdoll's 0.034975 m anchor error is about 3.3x the projected bridge's 0.010674 m.
  It is not the worst error in all configurations: the unprojected 100-link chain is larger.
- Scene 8 is the only row with a CCD event, and it needs exactly one, with no cap and no
  clamp: the bullet rests against the wall.

Reading the table:

- **Thousands of bodies actually colliding costs far more than the settled scene.**
  5,000 awake bodies in persistent contact: **40.2 ms** p50 with NGS projection on, and
  **86.8 ms** p50 when the contacts churn. Both are far past a 16.67 ms budget. The
  separately-accounted sleeping case is the same field asleep at **13.7 ms** p50 with
  `awake = 0`, which is the frozen-pair regime, not an active one.
- **NGS projection, not the solver, dominates the awake case.** The adjacent
  `stress5k_awake_no_ngs` pair differs only in `positionCorrection`: 40.2 ms against
  18.6 ms, so projection is about **21.6 ms of a 40.2 ms frame**. `correctPositions`
  re-runs narrowphase per manifold per iteration, and it skips sleeping pairs - which is
  why `book` collapses from 23.8 ms awake to 1.4 ms asleep.
- **The tail is worse than the median.** p99 reaches 126-143 ms awake against a 40 ms
  p50, and single frames exceeded 170 ms. Median-only quoting would understate the
  interactive cost.
- **The CCD stage is measured, not assumed.** `ccd_stream_8_bullets` is dominated by
  `ccd` (0.051 of 0.050 ms p50) because eight swept bullets cast every frame; CCD is
  exactly 0 in every other case because none of them contains a bullet.
- **Host-load variance is large and is reported, not smoothed.** The fixed 20M-FMA
  calibration moved **+69.9%** (56.4 ms to 95.9 ms) across this run, so figures from
different cases are not interchangeable. Only two comparisons in the table are
  trustworthy: the adjacent NGS-on/off pair, measured back to back, and within-case spread
  (p50 ranges of 1-4% for the stress cases). The browser-stress section below quotes
  13.3-15.3 ms for the resident step, which is not evidence that this host is slow.

Reproduce, keeping exit statuses:

```bash
set -euo pipefail
```

The program exits non-zero if any case produces a non-finite body state, exhausts its

count. CMake exposes the same program as the `benchmark_active` target.

## Browser stress scene driven with continuous input

The showcase's own read-outs were driven in Chromium through the same entry points the UI
calls (`_select_scene`, `_spawn_box`, and the pause/step path), because the preview tab
reports `visibilityState = hidden` and therefore throttles `requestAnimationFrame`; the
page's tick accumulator then advances in catch-up bursts instead of real time. Pausing and
using `_step_once` gives exactly one `World::step` per call, so the reported EMA is a
per-step cost rather than a catch-up artifact.

| observation | bodies | awake | contact points | step EMA |
|---|---:|---:|---:|---:|
| fresh stress field, after 10 steps | 5001 | 5000 | 2000 | 14.14 ms |
| after 20 steps | 5001 | 5000 | 8000 | 25.53 ms |
| after 30 steps | 5001 | 5000 | 10000 | 33.37 ms |
| settled and slept (270 steps) | 5001 | 0 | 1000 | 13.30 ms |
| 20 boxes spawned over 80 steps | 5021 | 5020 | 10020 | 44.65 ms |
| one real `+ Box` toolbar click and one real canvas click | 5022 | 5021 | - | 44.30 ms |

The last two rows are the point: a sleeping 5,000-body field (0 awake, 13.3 ms) becomes
active under continuous input (5,020 awake, 44.7 ms), and the UI's own AWAKE / BODIES /
CONTACT POINTS / step read-outs agree with the frame buffer. No console errors were
captured while driving it, and the 221-assertion Chromium suite asserts an empty page-error
list on the same build.

What this does **not** demonstrate: it is the WebAssembly build, not the native one, so it
cannot corroborate the native numbers above; the reported cost is the simulation step with
rendering explicitly excluded (the page says so itself) and no rendered-FPS measurement
exists; the tab was hidden, and the catch-up behaviour of a throttled tab is not a frame-cost
measurement; and the field is 300 m wide, so "continuous input" is a global wake-up of one
densely connected pile rather than a claim about sustained input on any other scene.

### Re-measurement during the presentation pass

The table above did not reproduce. Driving the identical scene through the identical entry
points on the same host gave a different shape, and the presentation pass hardened the driver
so the discrepancy is at least attributable: the suite now asserts the engine's simulated step
counter equals the number of driver iterations, which proves one `World::step` per call, where
the older receipt labelled driver iterations without that check.

[dashboard-drive.log](../build/browser-check/dashboard-drive.log).
Tests are still driven paused, one step per call. Scene 7 unless stated.

| configuration | bodies | awake | contacts | step EMA | dominant stage |
|---|---:|---:|---:|---:|---|
| island sleeping disabled, 5000 awake | 5001 | 5000 | 10000 | 13.1–17.9 ms | bookkeeping 44% (5.75 ms) |
| same, solver iterations 10 → 120 | 5001 | 5000 | 10000 | 43.1–47.3 ms | solve 31.0–33.6 ms |
| same, position correction off, iterations 120 | 5001 | 5000 | 10000 | 35.7 ms | solve 29.6 ms, bookkeeping 0.43–0.54 ms |

The seven stages reconcile with the step: Σ 13.00 ms against a 13.12 ms EMA, and Σ 20.18 ms
against 20.37 ms on a more loaded run — 99% accounted in both. Where the earlier table needed
"about 270" steps to reach sleep, this one needed 75; where it recorded 13.30 ms resident and
44.65 ms under continuous input, this one records 6.4–8.0 ms resident and reaches 44 ms only by
raising the iteration count. The direction of the difference is the same as the documented
host drift (the native run above calibrated +69.9% mid-sequence), but the method changed too,
so treat the older step labels as driver iterations rather than verified step counts. Neither
set is a rendered frame rate.

Two controls are worth singling out because they are visible on the dashboard as it runs:
raising `SolverConfig::iterations` from 10 to 120 took the solve stage from 2.8–3.3 ms to
31.0–33.6 ms, and clearing `positionCorrection` took `bookkeeping` from 5.8–7.6 ms to
0.4–0.5 ms. The second is the figure to quote for NGS: on an active 5,000-body contact graph
the projection pass, which re-runs narrowphase per manifold per iteration, is the single
largest line item, and it disappears when the option is off.

## What these numbers do not prove

- **They are not portable, and not even stable across sessions on this host.** One
  compiler, a shared machine, wall-clock timing, no pinning and no confidence intervals.
  The same dense 10k row read 71.757600 ms in the previous revision of this document and
  177.565200 ms here.
- **Broadphase speedups are not tree-only speedups.** The full-step comparison also skips
  narrowphase work on distant pairs, so `step_speedup` mixes two effects.
- **The sparse scenes have zero contacts.** Their timings say nothing about solver cost
  under load, and no memory, allocation, cache or threading counters exist in this
  historical measurements. Prepared-storage allocation counts are now available in
  [the storage regression](STORAGE.md#checks-and-performance), but are not timing or
  cache/threading evidence.
- **No rendered frame-rate claim.** Every millisecond here is simulation only; the SFML
  renderer and the WebAssembly build are not represented in these tables, and the
  5,001-body figure is a step cost of a shallow field.
- **Dense 10k does not fit a 16.67 ms budget** (177.565200 ms per full step in this run),
  which is why the interactive showcase scene is a 5,000-body shallow field.
- **Some rows are failure rows.** `stack20,0,0`, `stack20,1,0`, `pyramid15,0,1` and the
  100-link joint chain are measurements of known bad configurations. They are evidence
  about the engine's limits, not recommendations.
- **The correction table is one step of one scene.** The meaningful difference is
  2.599200 J of injected kinetic energy versus 0, not the timing.
- **The CCD table is narrow.** Only circles and one thin tilted polygon, only against a
  single static wall, with zero restitution, default material friction but no tangential
  incident velocity, no joints and no moving/rotating targets. `capped_trials = 0`
  only says no event cap was reported. Clamp/push-out/unconverged need their own counters.
- **The showcase table is scene-level, not operation-level.** It says what each demo
  costs on average, not where the time goes; for phase breakdowns, enable `world.profiling = true` in a native harness.
  The SFML demo already enables it and reports buckets in its title bar.

## Smooth-force integrator study

From the repository root, build/run the standalone oscillator study and plot its CSV:

```bash
set -euo pipefail
mkdir -p build
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -Werror -I. study_integrators.cpp -o build/study_integrators
./build/study_integrators
python tools/plot_energy.py
```

It writes `build/integrator_energy.csv` and `build/integrator_energy.svg`. The study is
omega=10, dt=0.01, 100,000 smooth-force steps; timings include sampled CSV output, not
pure policy microbenchmarks. It does not switch World's contact integrator. The local
energy receipt is separate from the broadphase/CCD/showcase CSV schemas.

## Reproducing a single number

To check one claim without reading any of the tables above:

```bash
set -euo pipefail
```
